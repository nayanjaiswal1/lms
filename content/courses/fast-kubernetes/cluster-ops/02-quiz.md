      prompt: After running `sudo kubeadm init` on the control-plane node, which commands are required to let a regular (non-root) user run `kubectl` against the new cluster, as shown in the lesson?
      multiple: false
      options:
          - text: Only sudo kubeadm init is needed; kubectl works immediately for any user without further steps
            correct: false
          - text: Create $HOME/.kube, copy /etc/kubernetes/admin.conf into it as config, then chown that file to the current user
            correct: true
          - text: Reinstall kubectl using a special --user flag on apt-get install
            correct: false
          - text: Run kubectl config set-context to switch the current user to root
            correct: false
      explanation: |
          The lesson's setup steps are `mkdir -p $HOME/.kube`, `sudo cp -i
          /etc/kubernetes/admin.conf $HOME/.kube/config`, and `sudo chown $(id -u):$(id -g)
          $HOME/.kube/config`. This copies the admin kubeconfig generated by kubeadm init and
          hands ownership to the current user so kubectl can read it without sudo.
    - id_key: q2
      type: mcq
      difficulty: beginner
      points: 2
      prompt: According to the lesson, what two pieces of information (besides the API server address) does a worker node need in order to run `kubeadm join` and join an existing cluster?
      multiple: false
      options:
          - text: The cluster's join token and its discovery-token-ca-cert-hash
            correct: true
          - text: The control-plane node's root password and SSH private key
            correct: false
          - text: The name of the CNI plugin and the Pod CIDR range
            correct: false
          - text: The kubeconfig file of another worker node that has already joined
            correct: false
      explanation: |
          The lesson repeatedly shows the form `kubeadm join <address> --token <token>
          --discovery-token-ca-cert-hash sha256:<hash>`. The token authenticates the worker with
          the control plane, and the discovery-token-ca-cert-hash lets the worker verify the
          control plane's identity. `kubeadm token create --print-join-command` is the easy way
          shown in the lesson to regenerate this full join command later.
    - id_key: q3
      type: mcq
      difficulty: intermediate
      points: 3
      prompt: In the lesson's 'Enable Dashboard on Cluster' walkthrough, after applying the Kubernetes Dashboard manifest and running `kubectl proxy`, how does the lesson obtain admin credentials to log into the dashboard UI?
      multiple: false
      options:
          - text: It creates a ServiceAccount named dashboard-admin-sa, binds it to the cluster-admin ClusterRole with a ClusterRoleBinding, then reads that ServiceAccount's token from its secret
            correct: true
          - text: The dashboard ships with a built-in admin/admin login
            correct: false
          - text: It reuses the same kubeconfig file that kubectl uses, pasted directly into the browser
            correct: false
          - text: It runs minikube dashboard, which disables authentication entirely even on non-minikube clusters
            correct: false
      explanation: |
          The lesson runs `kubectl create serviceaccount dashboard-admin-sa`, then
          `kubectl create clusterrolebinding dashboard-admin-sa --clusterrole=cluster-admin
          --serviceaccount=default:dashboard-admin-sa` to grant it admin rights, then finds its
          token with `kubectl get secrets` and `kubectl describe secret
          dashboard-admin-sa-token-...`, and pastes that token into the Dashboard's token login
          screen. The separate `minikube addons enable dashboard` path shown later in the lesson
          is a simpler option available only on minikube.
