# Code Flow Map

Feature-wise trace of every user-facing (and background) flow in MindForge: frontend entry point → API → Go handler → service/repo → DB tables, plus any non-trivial hop (AI call, job queue, websocket, cache, external service).

Generated by reading `docs/*.md` where a doc exists and the code directly where it doesn't. Cross-check against the relevant `docs/<feature>.md` before trusting exact request/response shapes — this map is for tracing *where code lives*, not a full API reference.

## Identity & Access

### Auth
**Frontend:** `app/login`, `app/register`, `app/verify-email`, `app/(app)/settings/security`
**API:** `POST /api/auth/{register,login,refresh,logout,verify-email,resend-verification,forgot-password,reset-password}` · WebAuthn: `POST /api/auth/webauthn/{login,register}/{begin,finish}` · `GET /api/auth/{me,csrf-token,webauthn/credentials}` · OAuth: `GET /api/auth/{google,github}`, `POST /api/auth/social/exchange`
**Handlers:** `backend/internal/auth/{handler.go, jwt.go, email.go, social.go, webauthn.go, provision.go}`
**Service:** `auth/context.go` (request-scoped session context) · `backend/internal/session/cache.go` (Redis-backed JTI blocklist + session-version cache, used for logout-all and forced re-auth on role/org changes)
**DB:** `users`, `email_verifications`, `password_reset_tokens`, `refresh_tokens`, `social_accounts`, `jti_blocklist`
**Notable hops:** SMTP for verify/reset emails · WebAuthn ceremony state held in Redis · OAuth callback issues JWT + session cookie

### RBAC / Authorization
**Frontend:** `app/(app)/admin/rbac/{permissions,roles,users,audit}`
**API:** `GET /api/me/permissions` · `GET/POST/PUT/DELETE /api/admin/rbac/{permissions,roles,users,audit}`
**Handlers:** `backend/internal/authz/{handler.go, handler_admin.go, handler_me.go, routes.go}`
**Service:** `authz/service.go` (permission resolve engine), `authz/admin_service.go`, `authz/cache.go`, `authz/middleware.go` (`RequirePermission` guards on every protected route)
**DB:** `permissions`, `roles`, `role_permissions`, `user_roles`, `audit_logs`
**Notable hops:** In-memory + Redis cache checked on every request · every RBAC change writes an audit row

### Organizations
**Frontend:** `app/org/`, `app/org-select/`, `app/(app)/org/settings/invites`
**API:** `POST /api/orgs` · `GET /api/orgs/me` · `POST /api/orgs/{switch,join}` · `GET/PATCH /api/orgs/{id}` · `POST /api/orgs/{id}/activate` · `/{id}/onboarding`, `/{id}/auth-config` · `/{id}/domains` (verify, auto-join) · `/{id}/invites*` (batch invite/resend/revoke) · `/{id}/members` · `/{id}/audit-logs`
**Handlers:** `backend/internal/orgs/handler.go`
**Service:** `orgs/{service.go, repo.go, member.go, invite.go, domain.go, onboarding.go}`
**DB:** `organizations`, `org_members`, `org_invites`, `org_domains`
**Notable hops:** Invite creation enqueues a background job · demoting/removing a member bumps `session_version`, invalidating their active sessions

### Onboarding
**Frontend:** post-signup flow under `app/(auth)/register`
**API:** `GET/POST /api/user/onboarding`
**Handlers:** `backend/internal/onboarding/handler.go` — single upsert, optional fields only written if present
**DB:** `user_profiles` — same table Profile reads/writes; onboarding fields (timeline, experience level, role intent, topics) live as columns there, not in a dedicated onboarding table
**Notable hops:** Feeds initial goal/time-commitment into Roadmap generation

### Profile
**Frontend:** `app/(app)/settings/profile` (authenticated) · `/u/{slug}` (public, no auth)
**API:** `GET/PATCH /api/profile/me`, `/me/overview`, `/me/avatar` (POST/DELETE), `/me/skills` (GET/POST/DELETE) · `GET /api/profile/{user/{userID}, public/{slug}}`
**Handlers:** `backend/internal/profile/handler.go`
**Service:** `profile/{service.go, repo.go}`
**DB:** `user_profiles`, `user_skills`, `users`
**Notable hops:** Avatar upload goes through `backend/internal/storage/{minio.go, storage.go}` (MinIO presigned URL; `noop.go` backs local dev without MinIO configured) — shared by any feature that stores a file

### Features (flags & entitlements)
**Frontend:** `<FeatureFlagProvider>`/`<AccessGate>` in app layout, checks `/api/me/features` at session start
**API:** `GET /api/me/features`
**Handlers:** `backend/internal/features/handler.go`
**Service:** `features/{service.go, repo.go}`
**DB:** `feature_grants` (per-user, keyed by feature_key) — no separate org-level table; org gating is resolved in the service layer
**Notable hops:** Frontend gate is UX only — backend re-checks entitlements on the actual API call

## Assessment & Interview

### Assessment & Batches
The largest backend package in the repo — question bank, test authoring, batch (cohort) management, attempt-taking, coding-submission grading, and offline test scores. `docs/assessment.md` does not exist yet; this section is sourced directly from `backend/internal/assessment/` and the migration.
**Frontend:** `app/(app)/assessments` (student attempt list, `[id]/take`), `.../assessments/manage` (instructor test builder, results, review, proctoring log), `app/(app)/question-bank`, `app/(app)/batches` (list, detail, courses, members, chat, progress, analytics, `[id]/tests`, `[id]/import`), `app/(app)/interview/{progress,skills}`, `app/(public)/hire/[code]`
**API:**
- Question bank/authoring: `POST/GET /api/categories`, `/api/questions*`
- Assessment authoring: `POST/GET/PATCH /api/assessments*`, `/questions`, `/publish`, `/status`
- Batch management: `POST/GET/PATCH /api/batches*`, `/members/{userID}`, `/image`, `/mentors`, `/courses`, `/invite*`, `/import/*` (parse/validate/confirm/report), `/progress`, `/analytics`
- Assignment & grading: `POST/GET/DELETE /api/assessments/{id}/assignments` · `GET /assessments/{id}/{analytics,attempts,candidates}` · `GET /attempts/{id}/proctoring` · `GET /api/analytics/overview` · `GET /api/interview/review-queue`
- Offline scores: `POST/GET/PATCH /api/batches/{id}/offline-tests*`
- Student attempt flow: `GET /api/my/{assessments,analytics,batches}` · `POST /api/assessments/{id}/attempts` · `GET /attempts/{id}` (resume) · `PUT /attempts/{id}/answers` · `POST /attempts/{id}/questions/{qID}/run`, `/events`, `/submit` · `GET /attempts/{id}/{result,evaluation,evaluation/status,compare/{other}}`
- Public/hiring (no auth): `GET /api/p/{code}` · `POST /start`, `/submit/{token}` · `GET /result/{token}`
**Handlers:** `backend/internal/assessment/{handler_assessment.go, handler_attempt.go, handler_batch_ext.go, handler_analytics.go, handler_dashboard.go, handler_interview.go, handler_offline_tests.go, handler_public.go, handler_import.go}`
**Service:** `assessment/service.go` (orchestration, grading) · `assessment/repo*.go` (per-domain query files) · `assessment/executor.go` (coding runner selection) · `assessment/evaluator.go` (AI subjective grading)
**DB:** Question bank — `questions`, `question_versions`, `question_categories`. Assessments — `assessments`, `assessment_questions`, `assessment_assignments`. Attempts — `assessment_attempts`, `attempt_answers`, `attempt_events` (anti-cheat log). Coding — `coding_submissions`. Batches — `batches`, `batch_members`, `batch_mentors`, `batch_courses`, `batch_member_details`, `batch_invitations`. Offline — `offline_test_scores`.
**Notable hops:** Coding submissions run through Piston (preferred) or Judge0, selected in `executor.go` · subjective answers queued as `eval.subjective` jobs, graded by Claude against a 7-dimension rubric (`evaluator.go`), result in `attempt_answers.ai_feedback` · assessment embedded in a course module calls back into `courses.MarkModuleCompleted` and `rewards` on pass · Excel batch import is a 3-step async parse/validate/confirm workflow staged in `batch_member_details` with rollback · anti-cheat events are logged, not ML-flagged in real time

## Cross-cutting patterns

- **Auth on every request:** JWT in an httpOnly cookie → `auth` middleware → org context + `authz.RequirePermission` guards route access.
- **Multi-tenancy:** every domain table carries `org_id`; queries are scoped by the authenticated user's org claim.
- **AI discipline:** check DB/cache first, call the LLM once, persist the result — enforced repo-wide, not just in Highlights/Roadmap.
- **Background work:** anything slow or bursty (AI generation, email, calendar push, escalations) goes through `jobs`, not inline in the request handler.
- **Frontend → backend:** all server-side calls go through `lib/server/api.ts` helpers (`apiGet`/`apiPost`/`apiAction`/`apiUpload`); client components use `lib/client/api.ts`'s `apiFetch`. No raw `fetch()` with hand-built cookie headers outside the documented exceptions.
