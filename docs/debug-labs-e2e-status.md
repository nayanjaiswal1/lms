F8 ROOT CAUSE (2026-10-09, confirmed from server.log 23:06-23:26 + Node repro): not a concurrency race. frontend/proxy.ts appended the refresh response's Set-Cookie headers, then trackLastPage() called response.cookies.set(LAST_PAGE_COOKIE); NextResponse.cookies.set() rebuilds the Set-Cookie list from its own map and drops raw headers appended earlier, so the rotated refresh_token/access_token/csrf_token never reached the browser whenever the page differed from the last_page cookie. The browser kept replaying the parent token: 23:06:11 rotate (200), 23:06:35 in-grace replay (200, access only), access token expired 15m later, 23:22:26 replay 16 min after rotation -> reuse detection (58B body = "Session reuse detected...") -> family revoked -> logout. The later 401 "pairs" are two proxied requests per navigation reusing one keep-alive connection (sequential, same port), each replaying the dead token because the proxy also dropped the backend's clearCookies on the 401 redirect. FIX: (1) proxy.ts appendSetCookies() runs after trackLastPage and also forwards Set-Cookie on the 401 login redirect; (2) backend successor is now HMAC(COOKIE_SECRET, parent) so an in-grace replay re-emits the identical successor refresh cookie (idempotent across racing requests / lost responses), in-grace replay with a dead successor -> 401 without revoking, after grace -> revoke family as before (auth/handler.go classifyReplay, auth/jwt.go successorRefreshToken; tests in auth/refresh_grace_test.go incl. DB-backed TestHandleRefreshReplay). Needs backend rebuild + frontend restart to verify on the stack.
